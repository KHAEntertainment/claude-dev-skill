# Phase 1 — 产品对齐

模块化渐进对齐 + 词语精度沉淀 + 必要时原型驱动。
**不消除所有模糊点，不进入 Phase 2。**

---

## 顶部锚定原则（贯穿整个 Phase 1）

1. **一次只问一个问题**，问完等用户回答，不批量提问
2. **每个问题都附带 AI 推荐答案 + 一句理由**，让用户做"是/否/微调"，而不是从零思考
3. **不设提问上限**——只在用户主动按下"满意"的模块切换闸门才推进
4. **每轮显示进度面包屑**（见下方格式），用户不需要自己记"我们走到哪了"
5. **不假设、不重写用户已有文档**（除非用户明确要求）
6. **codebase 能查到的事先查代码再问用户**——已有项目里，调用关系、现有约定、模型结构应该读代码而非靠提问

**进度面包屑格式**（每轮回复开头都带）：
```
[模块 N/M: <模块名>] · 当前层级：<Big Picture | 行为 | 细节> · 已锁定：K · 待决策：J
```

- `K` 和 `J` 都是**非负整数**（决策计数）。把"待决策"想成"当前层级里还没拍板的具体问题数量"。
- **面包屑在 `J` 之后立即结束**，不要在尾部追加 `待决策：B.3 压测中` 或 `状态：闸门` 这种描述性字段——状态信息放在面包屑下面正文里说。
- **Pre-lock 阶段**（Step A 进行中、模块列表尚未锁定）面包屑形式：`[模块切分中] · 当前层级：Big Picture · 已锁定：0 · 待决策：N`（N 是 Step A 内剩余的顶层问题数）。不用 `模块 -/-` 这种形式。
- **多部分推荐答案的拆分原则**：如果一个 Q 的推荐答案会一次性锁定 ≥3 个**互相独立**的决策，应拆成多个 Q 分别问（"一次一问"针对的是决策粒度，不是问题数量）。若推荐答案的多个部分**互相耦合**（如 CLI 命令名 + 默认行为 + 输出格式属于同一 UX 决策束），可以打包成一个 Q，但要在推荐答案里清楚标注是 N 个子决策一起锁定。

---

## 入口分流

- **情况 A — 用户已提供需求文档**（满足全部三项）：
  - 有核心功能描述（不止一句产品方向）
  - 有目标用户或使用场景
  - 有技术约束或明确非功能要求

  → 以用户文档为 PRD 基础，**不重写**。直接进入 Step A 做模块切分；后续 Step B 仍按模块化渐进提问推进，把文档里没说清的部分逐一钉死。

- **情况 B — 用户未提供需求文档**：
  → 完整走 Step A → B → C → D，最终生成 PRD。

---

## Step A — 产品全貌 + 模块切分

### A.1 顶层提问（一次一个）

按以下顺序逐问，每个都带 AI 推荐答案：
1. 这是什么产品？做什么的？（一句话定位）
2. 谁用？典型使用场景是什么？
3. 部署形态是什么？（Web / 桌面 / API / CLI / 本地脚本）
4. 第一版（MVP）的边界在哪？明确**不做的事**是什么？

情况 A 时，如果以上信息文档已经覆盖，跳过该问题，仅在歧义处追问。

### A.2 模块切分草案

基于以上信息，**现场判断**这个产品应该怎么切模块，**不预设模板**：
- 非 AI 普通项目：可能是 `前端 / 后端 / DB / 部署` 之类
- AI Agent 项目：可能是 `前端 / Agent 核心 / 工具集 / 检索/记忆 / 模型层 / 部署` 之类
- 单机脚本：可能就是 `输入处理 / 核心逻辑 / 输出` 这种简单切法

输出格式：
```
基于上面的理解，我建议把这个产品切成以下 N 个模块来逐个对齐：
1. <模块名> — <一句话职责>
2. <模块名> — <一句话职责>
...
模块之间的依赖关系：<简述>
```

### A.3 锁定模块列表（必经握手）

明确询问用户：
```
以上模块切分准确吗？我们要按 1 → 2 → 3 → ... 这个顺序逐个对齐。
如果切分需要调整，请告诉我；如果 OK，回复"锁定"。
```

**用户未回复"锁定"或等价确认前，不进入 Step B。** 这一步看起来繁琐，但模块列表后续承担进度面包屑、术语归属、原型 slug 命名的锚定职责，不能漂移。

---

## Step B — 模块内循环

对锁定的每个模块，依次执行 B.1 → B.4，循环到用户在闸门按"满意"。

### B.1 三层渐进提问

按以下顺序由浅入深，每层走完再下钻：

**Big Picture 层**
- 这个模块的目标是什么？边界在哪？
- 跟其他模块的接口是什么？输入什么、输出什么？

**行为层**
- 用户/系统在这个模块里有哪些动作？
- 主要数据流是什么？
- 关键状态有哪些？

**细节层**
- 具体字段、UI 形态、技术选型
- 边界场景与异常处理

**层间下钻条件**：当前层用户明确表示"够清楚了"才下钻。不要 AI 自己拍板转层。

### B.2 词语精度 inline

**监测时机**：词语精度 watching **从 Step A 顶层提问的第一个回答就开始**，不是等进入 Step B 才启动。Step A 期间若发现术语漂移，**先标记**（在面包屑下方一句"我注意到你刚才用了 X，先标记一下，等进入对应模块时一起钉死"），**glossary 写入推迟到该术语相关的模块的 Step B 内**——这样 glossary 条目能挂到正确的模块上下文。

提问过程中，时刻监测用户用词。命中以下任一情况立刻打断流程做术语澄清：
- 用了模糊词（"账号 / 客户 / 用户 / 资源 / 任务 / 项目 / 消息" 等容易重载的词）
- 同一概念用了多个不同词
- 跟 glossary 已有定义冲突

澄清后**立即写入** `docs/glossary.md`（不要等模块结束批量写）：
```markdown
**<规范术语>**：<一句定义>
_Avoid_：<被替代的近义词列表>
```

文件不存在就创建。术语应该在主对话和后续 Phase 中**严格使用规范词**，包括 AI 自己的提问。

### B.3 场景压测（模块 close-out 前必做）

准备进入 Step C 闸门前，AI 必须**编 2-3 个具体边界场景**让用户走一遍：

```
进入模块 X 闸门前，我编了几个场景压测一下你对这个模块的理解：

场景 1：<具体情境，比如"用户在登录中断网后又恢复">
按你刚才说的设计，应该会发生什么？

场景 2：<具体情境>
...
```

用户能流畅走通才算通过。卡壳 → 回到 B.1 对应层级继续提问。

**用户主动 opt-out 的处理**：如果用户明确说"这个模块简单，不用压测了 / 我对这个没疑问 / 跳过吧"，**不要静默跳过**。处理方式：
1. AI 复述一遍 opt-out："好，你认为模块 X 的设计已经够清楚，不需要场景压测。"
2. 把这条 opt-out 作为一条**已锁定决策**写进当前模块的锁定列表（例如 "用户主动 opt-out 场景压测——风险后果自负"），让它显式出现在 Step D 冻结 PRD 里
3. 然后才进入 Step C 闸门

AI 自己永远不主动建议跳过 B.3。这条规则是防"用户带节奏跳过"而不是禁止用户决策。

### B.4 原型触发

任何时点检测到**低保真信号**（参见 `phase1-prototyping.md` 的信号清单），暂停当前提问，按 `phase1-prototyping.md` 派发原型 sub-agent。

派发完成后：
- 主对话**继续在原模块原层级**等用户基于原型回答
- 不要因为派了原型就跳到下一层或下一个模块
- 原型回流后基于 readout 重提原决策点

---

## Step C — 模块切换闸门

当前模块的 B.1-B.4 走完后，**立即把当前模块的锁定决策写入 `PRD-draft.md`**（追加或更新对应模块章节），然后明确询问用户：

```
[模块 N/M: <模块名>] 当前我们锁定了以下决策：
- <决策 1>
- <决策 2>
...

我已经把这些写进 PRD-draft.md，等所有模块完成后会冻结为 PRD.md。

这个模块还有任何模糊点吗？没有的话我切到下一个模块 <下一个模块名>。
（回复"切下一个"或指出还要追问的点）
```

**写入规则**：
- 文件路径：项目根目录的 `PRD-draft.md`
- 文件不存在则创建，存在则追加/更新对应模块章节
- 顶部包含进度元信息：`<!-- phase1-progress: module N/M locked at YYYY-MM-DD HH:MM, current=<下一个>, layer=<层> -->`
- 锁定列表与本次闸门展示给用户的内容一致

**用户主动按下"满意"才推进，AI 不自行跳模块**。这是"无上限提问"的真正落点。

切到下一模块时更新进度面包屑 `N/M` 计数。**禁止不写 PRD-draft.md 就推进**——会话中断时这是状态恢复唯一锚点。

---

## Step D — 全模块完成 → 冻结 PRD

所有模块走完后，输出冻结 PRD。

PRD 输出格式（人类可读，不强制 schema —— Phase 2 不靠字段 mapping 消费 PRD，只读它当上下文）：

```markdown
<!-- phase1-progress: ALL MODULES LOCKED at YYYY-MM-DD HH:MM -->
<!-- modules: 1.<名> 2.<名> 3.<名> ... -->

# <产品名> — PRD

## 一句话定位

## 目标用户与场景

## 部署形态

## 模块清单与依赖
（与 Step A 锁定的模块列表一致）

## 每个模块的对齐结果
### 模块 1：<名>
**目标与边界**：
**关键行为**：
**关键决策**：
- <决策 1>
- <决策 2>
**已知未决**（不阻塞 Phase 2，但 Phase 2 拆任务时要注意）：
**关联原型**（如有）：prototypes/...

### 模块 2：<名>
...

## MVP 范围
## V2 候选（明确推迟）
## 明确不做的事

## 技术约束

## 成功标准
```

输出后明确询问用户：
```
以上是冻结 PRD。Phase 2 将基于此拆任务。
请确认（回复"冻结"或指出需要调整的地方）。
```

**用户确认"冻结"后才进入 Phase 2**。

---

## 状态恢复协议（跨会话）

如果上次会话在 Phase 1 中途结束，本次再进入 `/dev` 时：

1. 读取项目根的 PRD 草稿（如果存在）的顶部进度元信息：
   ```
   <!-- phase1-progress: module 2/5 locked, current=3 (Agent 核心), layer=行为 -->
   ```
2. 读取 `docs/glossary.md`，恢复已锁定术语
3. 读取 `prototypes/` 目录，恢复已生成的原型清单
4. 用进度面包屑向用户汇报恢复结果：
   ```
   恢复 Phase 1 上下文：当前在模块 3/5 (Agent 核心)，行为层。
   已锁定决策 X 条，已生成原型 Y 个。
   要继续从这里走，还是回头审视之前的某个模块？
   ```

文件命名：Step D 之前用 `PRD-draft.md` 存于项目根，Step D 冻结后改名为 `PRD.md`。草稿更新时机和写入规范见 Step C 段落。

## 术语重审规则

Module N 的讨论可能发现 Module M 锁定的术语有问题。此时：

- **显式 surface**：在主对话明确说 "刚才在 Module M 我们把 X 定义为 Y，但 Module N 的场景下这个定义有冲突，建议改成 Z"
- **用户确认后修改 glossary**，同时回到 Module M 检查是否需要调整其已锁定决策
- **不静默改**：术语漂移会污染后续 Phase，必须显式

如果重审导致 Module M 决策需要大改，回到 Module M 重跑相关 Step B 子环节，**不要带着冲突继续推进**。

---

## Phase 2 回流处理

如果架构级变更等路径让流程回到 Phase 1：

- **不重跑全流程**
- 读取冻结 PRD，识别受影响的模块
- 仅对受影响模块重跑 Step B（必要时含 B.2/B.3/B.4），其他模块保持不变
- 完成后更新 PRD 对应模块段落，标注变更时间与原因
- Step D 不再生成全新 PRD，只更新版本号（在顶部加 `<!-- phase1-progress: REVISED at YYYY-MM-DD ... -->`）

---

## 禁止行为

- 不在 Step D 用户确认"冻结"前进入 Phase 2
- 不在 Step A.3 用户确认"锁定"前进入 Step B
- 不批量提问（一次一个）
- 不省略每个问题的 AI 推荐答案
- 不假设用户没明确说的需求
- 不在用户已有文档时重写文档（除非明确要求）
- 不为追求"快速完成"而跳过场景压测（B.3）
- 不让 sub-agent 替主对话锁定决策（sub-agent 只产 artifact + readout）
- 不静默修改已锁定的术语或决策（重审必须 surface）
